# Interior-design delivery v2

The only registered implementation is `interior-design-delivery` version 2. Generate it from a quality-gated v2 project with the registry command. Do not recreate a visually similar page.

The fixed structure uses the historical `su-design-classic` full-canvas shell: a pale edge-to-edge canvas, floating header, bottom-left navigation ordered `用户需求 / 设计稿 / 渲染稿`, bottom-center viewing tools, and bottom-right gesture guidance. `设计稿` is the default active view; `渲染稿` appears only when a current governed render exists. The governed audit stays embedded in the artifact instead of becoming a visual navigation destination. The 用户需求 view owns one fixed evidence workspace containing the user-uploaded source-plan image, the Agent-uploaded revision-annotation image, requirements, professional boundaries, and revision history; there is no separate 户型图 navigation destination. The render switches within the same fixed, non-scrolling stage, uses the whole available frame without an inner scrollbar, and carries a visible concept-render boundary. Floor-plan evidence uses visible zoom out, scale, zoom in, and fit controls with low-sensitivity continuous wheel zoom, damped double-pointer pinch, double-click zoom, and drag after zoom in a 100–400% range. The render uses the same zoom and pan behavior plus left/right 90-degree rotation controls, visible angle feedback, and one fit action that restores rotation, scale, and position. Changing the floor-plan evidence resets it to fit. The Page also includes the Pascal design model, floor selection, real doors/windows and key components, visibly distinct 3D/orthographic views, labels, desktop/mobile-landscape layouts, concept comparison when multiple concepts exist, stacked/solo/exploded levels, issue and requirement highlighting, assumptions, unknowns, professional verification, revision summary, and a model-derived SVG failure fallback. A justified single-concept delivery hides the meaningless concept switch.

The Page must warm the viewer automatically. A dedicated loading surface, not a model-derived plan, covers the Canvas until the first valid frame. Labels and viewing controls stay unavailable during that interval, and scheduled invalidations cover cold-start layout and font timing. Displaying 3D may never depend on a click, drag, mode switch, or other user input. A real viewer error may reveal the accessible model-derived SVG fallback. The 3D control uses an isometric perspective pose; the 平面 control uses a top-down orthographic pose and late stabilization may not reset it to perspective.

The Page is a read-only artifact. It cannot save scene changes, call MCP or Agent tools, read files, access loopback, load remote content, execute evidence markup, or contain Space/owner/managed-object IDs. CSP denies network, frames, plugins, external fonts, workers, media, and form submission. Only the redacted user source-plan image, redacted Agent revision-annotation image, an optional registered render, and minimal viewer payload are embedded. The 用户需求 evidence workspace renders both evidence images with ordinary `<img>` elements and performs no SVG, Canvas, or DOM annotation drawing. The source image hash, project provenance, selected concept, compiled scene model basis, and Page payload must agree; this ensures 3D, orthographic plan, labels, and design explanations are derived from the displayed user upload rather than a generic template model.

The render is generated outside the Page only after explicit authorization permits the selected SU-derived reference to be sent to the image-generation provider. Register it through `render register` with the exact reference, prompt, generator, and current revision. The sidecar records scene, model-basis, image, reference-image, and prompt hashes. Page generation rejects stale or altered registered renders. It embeds only the accepted image and non-sensitive provenance, never the prompt or SU reference file. The render remains a concept visualization and does not replace the Pascal scene, evidence, technical validation, material sample, or professional review.

Generation writes exactly `index.html`, `scene.json`, `audit.json`, `template.json`, and `manifest.json`; the directory limit is 20 MiB. The verifier scans template metadata, CSP, remote executable assets, Pascal/CDN hosts, loopback/file URLs, development paths, source maps, and private identity fields.

The built-in catalog example is not a separately authored preview. `scripts/build-template-example.mjs` initializes `examples/professional-template/seed.json` as a governed project, compiles its Pascal scene, runs the same professional audit, registers the ImageGen render and exact SU-reference/prompt hashes, calls the same Page generator, derives an isometric `cover.svg` from the selected model, and records seed, evidence, render, project, scene, audit, and file hashes in the committed manifest. The built-in example also enforces a non-regression floor of 12 rooms, 30 procedural furniture/equipment items, 14 openings, 8 doors, and 6 windows, plus model labels and requirement highlighting. These thresholds protect the catalog quality reference; customer projects must reflect actual evidence rather than inventing elements to satisfy the example floor. `--check` regenerates the artifact and fails on any byte or quality drift.

Publication uses `pa-cli pages publish --template interior-design-delivery`. The CLI rejects an unknown template or any HTML whose meta/body marker, template ID, or version differs from the registry, computes the current contract digest and exact artifact SHA-256, and the Node re-verifies both before storing them under `page.template`. Record the returned immutable Page ID and template provenance. Natural-language changes return to the main Agent, create a structured revision, rerun the gate, generate a new artifact, and publish a new version. Rollback selects a previous immutable artifact.

Automated acceptance covers code, schema, scene, semantic HTML, accessibility markers, CSP, privacy, routes, size, deterministic hashes, the classic layout marker, and the automatic viewer lifecycle contract. Do not mark visual acceptance passed. Report `visualAcceptance: user` and keep it pending until the user reviews desktop and mobile interaction.
